## Paired restricted packed RGBA vs checked four-plane source-over

Both paths implement the **same tested linear-light source-over formula** at
fixed opacity **0.37**, but expose different full-domain layout, runtime
parameter, error and alias contracts. The packed path is
`RasterView!color.SRgba8` and public `raster.zipTransformInto`, which
already detects physical input/output overlap before the first write.
All packed output pixels are **byte-equal** to the four-plane version in the
test fixture; the probe validates overlap rejection and full source
preservation.

| Image dimensions | Paired rounds × complete passes | Four-plane median/round | Packed median/round | Throughput four / packed | Ratio of median timings |
|---|---:|---:|---:|---:|---:|
| 512×512 | 7 × 4 | 212.514 ms | 171.319 ms | 4.934 / 6.121 MPix/s | **1.240×** |
| 2048×2048 | 5 × 2 | 1679.481 ms | 1375.703 ms | 4.995 / 6.098 MPix/s | **1.221×** |

At this limited fixture the packed path achieves **22.1–24.0% higher
throughput**, equivalent to **18.1–19.4% lower elapsed time** for the same
work. The within-round paired ratios range 1.205–1.307 (2048²) and
1.229–1.271 (512²). These are observations on one unsupported-toolchain
local environment, not a general claim that all image compositing accelerates.

All **12** packed rounds have `pixel_differences=0` and
`PACKED-PROBE PASS`. This validates differential equality on the test
fixture, not the general four-plane API or its broader 432-scene independent
color oracle.

## Diagnostic full source-over vs checked access-only control

The control uses eight checked byte reads, byte XOR, and four checked
byte writes. It is **not the same calculation as source-over**.
Numerical/branch/cache cost attribution requires further profiling.

| Input semantics / layout | 512² composite MPix/s | 2048² composite MPix/s | 512² checked-access control MPix/s | 2048² control MPix/s |
|---|---:|---:|---:|---:|
| encoded sRGB / interleaved | 4.96 | 4.87 | 74.61 | 76.06 |
| encoded sRGB / planar | 4.49 | 4.46 | 71.49 | 72.52 |
| linear premultiplied / interleaved | 8.22 | 7.82 | 75.09 | 70.61 |
| linear premultiplied / planar | 8.16 | 7.96 | 74.87 | 74.05 |

Across **48** full-compositing rounds the two `gcBytes` columns are
always zero; each scenario's final output checksum is constant and
planar/interleaved variants agree. This proves no **current-thread GC-byte
increase in measured calls**; it does **not** prove zero native allocations,
zero peak operation scratch or a complete independent pixel oracle at 2048².

## Process memory caveat

The 2048² four-plane process groups report **69,404–69,536 kB** max
resident set, and the packed-vs-four-plane differential process reports
**101,652 kB** with six separate retained input/output buffers.
These are total **process RSS**, not isolated compositing scratch budgets.
The first 512² encoded/interleaved process reports **196,100 kB**,
far above the other 512² runs (~69 MB), and is not a credible operation-only
allocation claim: the runner timed `dub run`, which may start compiler
children/rebuilds, even though the *inner* stopwatch excludes setup.

The subsequent research runner improvement executes built binaries directly,
and offers an isolated `--pinned` mode using **read-only `git archive`**
to snapshot exactly tagged raster/color dependencies in ignored imagery-d
`data/` without modifying sibling repo HEADs. A small `--smoke` mode
supports actual CI verification of that mechanism.
